Language design and build plan

Borsuk

An FSM-first programming language for verified distributed systems

Borsuk is a proposed language for stateful software that runs on many machines. A program is a set of explicit state machines. Each machine has typed inputs, private state, and a public contract that a checker can verify. This page describes the design and the ten phases that build it.

  • DesignDraft of 18 November 2026
  • BuildNot started
  • MeasuredNothing yet

The name honors Karol Borsuk, a Polish mathematician known for his work in topology.

Overview

What Borsuk is for

Borsuk targets high-throughput software that keeps state, for example a booking service. Many agents change this software at the same time. An agent is a person or an AI coding agent.

An agent that changes one module must be able to read its contract, change its implementation, and find exactly which guarantee it broke.

  • Behavior
  • Ownership
  • Compatibility
  • Resource use

The main workload: one durable state change, end to end

  1. Send a commandThe caller sends a command with an ID. The caller keeps the ID for retries.
  2. Decide durablyThe system decides the command and writes the decision to durable storage.
  3. Reply can be lostThe network can lose the reply. A timeout leaves the result unknown to the caller.
  4. Retry, get the same answerA retry with the same ID returns the original decision during the published lookup window.

Three original commitments

Strong types across boundaries

Messages, replies, IDs, and the legal next steps have types. This includes traffic between services.

Explicit state machines

State changes only through declared transitions. A transition is a function from state and input to the next state.

Strict modularity by default

A module hides its representation. Other modules see only its declared interface and guarantees.

Language

The five language rules

A language rule decides three things: whether a program is well formed, what the program can do, and what a caller may rely on. Tools help people and agents write, check, and ship a program. The standard library and the runtime sit between the two. The language states a guarantee, a library selects it for an operation, and the runtime implements it.

L1

Public boundaries are typed protocols

Domain IDs, payloads, replies, and the legal next steps have types. Foreign input becomes a typed value only after validation. The wire format and the SDK are replaceable.

In practiceA single-use hold token tells a client that it may try to confirm. The service still decides expiry, duplicates, and revocation.

L2

State changes through explicit, functional transitions

Each state owner declares its control states, its data, its initial state, and its permitted edges. A turn takes the state and one typed input. It computes the next state and a description of effects. External results come back as new inputs.

In practiceLocal variables, pure helper functions, and scratch data need no actor and no mailbox.

L3

Modules are private by default

Each module owns its representation. Dependencies and observable effects cross an explicit signature. When modules compose, each environmental assumption needs a provider, or it must show at the outer boundary.

In practiceA caller uses the exported guarantees of a module. The caller never reads the implementation.

L4

Ownership and visibility govern mutation

A transition may update unique storage in place if every promised observation stays the same, including failures and cost bounds. A borrow cannot escape its lifetime. A successful handoff publishes prior writes to the receiver. A rejected handoff leaves ownership with the sender.

In practiceA full queue rejects a packet. The sender still owns the packet and can use it again.

L5

Named behavioral specs have a conformance meaning

A spec states safety laws, conditional progress, and scoped resource bounds. An implementation must accept the contracted inputs, and its observable behavior must refine the spec. A caller relies on a law as proved only when its obligations are discharged for that scope.

In practiceSeveral machines can implement one spec with different private states, algorithms, and storage layouts.

Safety lawA bad event never happens. Example: two bookings never own one slot.
Progress clauseA good event eventually happens, under stated assumptions. Example: an accepted command eventually gets a decision.
RefinementEvery observable behavior of the implementation is a behavior that the spec allows.

L3 makes the module the unit of change. L5 says when one implementation can replace another across that boundary. The compiler erases proof evidence when execution does not need it. A finite state machine can still have infinitely many configurations through its data.

Example

What a program looks like

The syntax is not final. This specimen uses Candidate A. It defines a reading type, a public spec with one law, and a private machine with two states.

telemetry/peakCandidate A
module telemetry.peak

pub type Reading = distinct i64 derives Ord

pub spec Peak {
    event Sample(Reading)
    query Read() -> Option<Reading>

    law read_peak {
        Read() returns history.values(Sample).max()
    }
}

machine PeakTracker implements Peak {
    state Empty | Seen(Reading)
    init Empty

    on Empty    + Sample(x) -> Seen(x)
    on Seen(hi) + Sample(x) -> Seen(max(hi, x))

    on Empty    + Read() -> stay, reply None
    on Seen(hi) + Read() -> stay, reply Some(hi)
}
  • distinct i64A Reading is stored as a 64-bit integer. The checker does not let it mix with other integers.
  • pub spec PeakThe public contract. Other modules see only this part.
  • law read_peakRead() returns the largest sample so far. With no samples, it returns None. The law talks about the input history. The machine does not store that history.
  • machine PeakTracker implements PeakA private implementation. It keeps only the current maximum. The checker must show that it refines Peak.
  • on Seen(hi) + Sample(x) -> Seen(max(hi, x))One transition: source state plus input gives the next state.
  • stay, reply Some(hi)The state does not change. The machine sends a reply.
  • ResetIf you add a Reset input to the spec, the checker reports each state that has no rule for Reset.

Two syntax candidates

A · One edge per declaration

on Seen(hi) + Sample(x) -> Seen(max(hi, x))
on Seen(hi) + Read()    -> stay, reply Some(hi)

Each transition is one complete line. A review can quote or move it alone.

B · Reactions grouped by source state

state Seen(hi) {
    on Sample(x) -> Seen(max(hi, x))
    on Read()    -> stay, reply Some(hi)
}

All actions of one state are in one place. A reader sees what the state can do.

Both candidates must make the order of effects easy to read. After the choice, a formatter gives one canonical form, so equal edits give equal diffs.

Effects come back as inputs

A spec for the booking case: DurableReschedule

Public lawObligation for each implementation
Acknowledged decisions survive recoveryAfter a caller receives a committed result, recovery keeps that decision for the published retention window. A crash between an early reply and the durable commit breaks this law.
Retries agreeInside that window, every definitive reply to a retry with the same ID and payload reports the original decision. A lost reply leaves the caller free to retry.

Both laws are safety laws. A machine that never replies satisfies both. So the spec needs a separate progress clause: an accepted command eventually gets a recoverable decision. That clause must state its delivery, scheduling, and recovery assumptions. A later reschedule with a new ID may move the appointment again. For an upgrade, a replacement may accept more inputs and give stronger guarantees. If it needs more from callers or promises less, that is a contract change.

Architecture

How a program runs

Borsuk owns the meaning of a program from source to optimization. The compiler, the runtime, and the shared tools are written in Rust. The backend translates Borsuk into LLVM IR and produces native code before the program runs. All tools read the same typed IR, so the interpreter, the verifier, and the optimizer agree on one meaning.

ComponentJob
Frontend and typed IRResolves types, state variants, input policies, ownership, effects, and resource obligations. Keeps these facts available for layout, specialization, storage reuse, and fusion. The public protocol and its laws do not depend on the private representation of a machine.
Reference interpreterRuns the typed IR in a simple way for differential tests and trace replay.
VerifierGives a precise meaning to the same operations. Uses Lean 4 for core theory, for example that a well-typed step preserves ownership. Verus is a candidate for selected Rust runtime parts.
Native backendChooses compact representations and lowers calls and transitions to LLVM. Uses cross-module and profile-guided optimization where measured workloads benefit. Checks resource contracts against lowered code and reports assumptions that foreign code adds.
Rust runtimeAn embedded machine runs on its caller's thread with caller memory. Independent scheduling uses a bounded mailbox. An in-process transfer can move an owned buffer. A process boundary adds encoding and transport costs. Sharding, batching, and group commit must respect the visibility and durability guarantees.
Agent toolchainThe CLI, the MCP server, and CI call one Rust library. A result has the same law ID, assumptions, evidence status, and scope at each entry point.

Optimization that the protocol permits

For the input below, the replies must be Some(90) and Some(120). Inside a run of samples, the compiler can combine the max operations into one update. This removes per-event dispatch and stores, and a numeric run can also use SIMD. A Read splits the run.

Cost target for one embedded transition

A transition from Held to a same-size successor on uniquely owned storage should compile to a tag check, a guard, and the required stores. For that path the target is zero heap allocations, zero payload copies, and zero scheduler hops. A proof that the compiler erases adds no instructions. A durable reply still pays for its storage flush or quorum. An allocating diagnostic on the queue-full branch breaks an all-path zero-allocation promise.

Finite models already run

An adversarial review of the design explored three small models by breadth-first search over all reachable states. Each model compares a permissive meaning with the proposed correction.

ModelShortest failure, permissive meaningResult with the correction
Retried credit with a crashApply the credit, crash and restart, retry. The credit applies twice. Identical replies do not prove a single application. 8 statesCommit the mutation and its completion record as one recoverable step. No duplicate. 3 states
Two peers, bounded queuesEach peer must send twice before it receives. With capacity 1, both queues fill and neither peer can move. Fair scheduling cannot enable a disabled step. 4 statesAt capacity 2, no deadlock. 19 states. This holds only for this protocol. Check the deployed capacities.
Cached proof after an editProve revision A, edit to B, accept the proof of A for B by law name. 7 statesRequire an exact revision match. No false acceptance. 6 states

A finite witness for the booking rules: 38 states, 106 transitions

Two request IDs compete once for one slot through a one-entry durable inbox. The owner can crash and restart, commit atomically, lose a reply, serve a retry, and expire a decided ID. The search found no violation of single ownership, inbox capacity, reply consistency, crash preservation, or terminal expiry. The model assumes an atomic durable commit. It tests no real storage, MCP client, implementation, or hardware.

A green proof can hide a weak spec

A proof can still pass after someone deletes the most valuable promise. So the toolchain inserts faulty implementations and checks which ones still verify. It also derives black-box tests from specs and compares implementation traces with the design.

Acceptance case

Reschedule one appointment under contention

This case tests both kinds of mutation in one workflow: a durable change that clients can see, and an efficient change of local memory. Two clients compete for one destination slot. A stale timer from an earlier hold arrives. The winner's commit reaches durable storage, but its reply is lost. The owner restarts during a rolling upgrade. The ingress queue fills while the client retries.

CheckRequired outcome
Client and protocolThe client keeps the same command ID across retries. A timeout leaves the result unknown. After a decision, the service keeps it for the lookup window. A definite rejection keeps the original appointment. Foreign clients pass the same wire validation and replay checks.
Atomic visible mutationAt most one booking owns the destination. A successful move frees the old slot and claims the new one as one logical step. The deployment states if it uses one transaction boundary or a cross-shard protocol, and the checker verifies that choice against the same public history.
Failures and recoveryA delayed timeout for hold A cannot release hold B. After commit and crash, a retry returns the original durable decision inside the recovery window. A recognizably expired request ID gets OutcomeExpired and does not run again. Notifications may arrive twice, so their guarantee states what the downstream service supports.
Efficient local mutationDecode into a preallocated packet. A successful queue admission transfers ownership. A rejection returns it. All pool buffers are conserved, including queued and in-flight packets. The declared allocation bound holds on both branches.
Progress and overloadWhen the recovery, delivery, and scheduling assumptions hold, every durably admitted command eventually gets a durable decision. The spec says when the service must admit a request and when overload permits a rejection. Acceptance, completion, and receipt stay distinct.
Real deployment and changeThe test uses real codecs, storage adapters, rolling versions, and the client retry path. A simulator counterexample replays against the smallest configuration that shows it. Client-observed histories are compared with the protocol.

The regression test

Move the success reply from after the commit to right after the enqueue. The message types and the happy path stay correct. A crash between the reply and the commit breaks the public guarantee. The agent must receive that crash trace.

How to compare with Rust

Use a hand-written Rust implementation with the same durability, batching, overload policy, hardware, and failure workload. Report offered and completed throughput, p50, p99, and p99.9 latency, rejection rate, bytes allocated or copied, and recovery time. Include hot-key skew and saturating load.

Adoption

Built for coding agents

The human describes the outcome. A coding agent can start without knowing a Borsuk keyword or a module name. The language ships a prompt like this one. The prompt guides the agent. The public spec has authority over behavior.

  1. Find the ownerSearch by intent returns the owning module.
  2. Read the contractThe pinned spec and one tested example.
  3. Change the codeEdit the private implementation.
  4. VerifyRun the same checker as CI.
  5. Replay a failureRun the counterexample from its recorded schedule.
Agent needProposed tool
Find the owner, learn the idiomA search tool accepts an intent or an exact symbol. It returns the owning module, stable spec and law IDs, the package version, and links to short docs and examples checked against that version.
Check a changeA verify tool calls the same checker as CI. Its structured result names the input revision, the dependency and toolchain identity, the affected laws, assumptions, proof status, and bounds. Diagnostics carry source spans, the observed violation, and candidate repairs when available.
Understand a failureA replay tool runs the counterexample with its recorded inputs, versions, and schedule. The CLI gives the same operation for clients with incomplete MCP support.

Why the search tool must stand alone

MCP separates prompts, resources, and callable tools. Host support and context selection vary. So the search tool must work when a host does not attach documentation or prompt templates on its own.

How adoption is measured

Three arms: the existing host-language workflow, Borsuk with local docs and CLI, and Borsuk with guided prompts and MCP. Trials include stale docs, full queues, changed revisions, and a shortcut that weakens the public law. Record verified task success, false proof claims, human interventions, time, and tokens. Real adoption: pilot teams choose a second workflow after the first succeeds.

Status

What is not established

  • No formal semantics. The full language still needs typing rules, evaluation rules, and soundness proofs.
  • No implementation. No compiler, runtime, checker, or agent tool exists.
  • No benchmark. Every performance number on this page is a target.
  • No agent trial. No agent benchmark or adoption trial has run.
  • Abstract models. The finite models assume an atomic commit. They test no real storage, MCP client, implementation, or hardware.
  • Trace comparison is not proof. Interpreter and native traces give evidence. Compiler correctness needs its own refinement argument.

Reference

Glossary

FSM (finite state machine)
A program part with a fixed set of control states. An input moves it along a declared edge to the next state.
Transition, turn
One step of a machine. It takes the state and one input, and gives the next state, replies, and effect requests.
Effect
A request to the outside world, for example a storage write. Its result returns as a new input.
Protocol
The legal order and types of messages between two or more parties.
Session types
Types that describe a protocol, including what may happen after each message.
Spec, law
A spec is a named public contract. A law is a property that every permitted history must satisfy.
Refinement
Each observable behavior of the implementation is a behavior that the spec allows.
Proof obligation
A statement that the checker must prove before a caller can rely on a law.
Model checking
A check that explores all reachable states of a model, usually within bounds.
Deterministic simulation
Test runs where the scheduler, clock, and faults come from a seed, so a failure replays exactly.
Typed IR
Intermediate representation: the checked internal form of a program. All Borsuk tools read it.
LLVM
A widely used compiler back end that turns LLVM IR into machine code.
Ahead of time
Compilation to native code before the program runs.
ThinLTO, PGO
Link-time optimization across modules, and optimization that uses measurements from real runs.
SIMD
Processor instructions that apply one operation to many values at once.
Ownership, borrow
Ownership says which part of a program may change a value. A borrow is temporary access that ends at a known point.
Mailbox
A bounded queue of inputs for a machine that runs on its own schedule.
Retry identity
A command ID that the client keeps across retries, so the service can recognize a repeat.
Lookup window
The time during which the service keeps a decision, so a retry can find it.
Group commit
One storage flush that makes many commands durable.
p99.9 latency
The latency that 99.9 % of requests meet or beat.
MCP
Model Context Protocol: an open standard that lets AI agents call tools and read resources.
Lean 4
A proof assistant and programming language for machine-checked proofs.
Verus
A tool that verifies Rust code against written specifications.
