Borsuk Language Core

A language for services of every size, from a personal blog to a payment system. Coding agents write it. People read it through tools.

This document describes the design of version 0.1. Each section says what a part is, how it works, and why the language needs it. You do not need to know how languages are built. Section 2 follows one request through a running system. A consistency check near the end tests whether all parts fit together.

1 · Why

What the language is for

Borsuk is for services of every size. A personal blog, a pet website, a shop, a booking system and a payment service all fit. Each one holds state and changes it on request. A caller sends a command. The service decides it, stores the decision so that it survives a crash, and replies. If the reply is lost, the caller can ask again and gets the same decision.

A small service uses a small part of the language. The largest services set the hardest rules, so most of this document describes them.

SizeExampleWhat it usesWhat it never pays for
SmallA personal blog, a pet website, a command-line toolOne node. In-memory machines or durable local. The HTTP or CLI platform.A cluster, consensus, transactions. A machine with no durability name compiles with no store code.
MediumA shop, a booking system for one clinicThree nodes in one region. durable quorum(1). pending and decide for payments.Copies in other regions
LargeA booking platform, a payment serviceMany nodes in several zones or regions. durable zonal or durable regional. Transactions and global protocols.Nothing. It uses the whole language.

One language and one set of rules for each size. A service can grow from one row to the next. It changes its durability names and its deployment file, and the runtime moves its stored data. Its cells do not change.

Today, teams write these services by hand in Rust, Go or Java, with a database, a queue and many conventions. Three mistakes are common. A service replies before the data is safe. A retry runs a command twice. A timer fires for an old request and changes new data. Borsuk makes the rules against these mistakes part of the language, and its tools check them.

  2. One way per thingEach concept has one construct, and normal-form rules remove equal variants. The goal is one accepted text for one behavior.
  3. Laws that tools checkEach machine states laws. Tools check them and report the kind of evidence: a proof, a bounded check, or a sample.
  4. Fast and distributedThe target is at least 95 % of the speed of expert hand-written Rust with the same durability, on one node or on many.

3 · Code

Three kinds of code

Most code waits for nothing. It computes a price or parses a message. That code is a plain function. Code that asks the outside world for something must wait for the answer. While it waits, it needs a place to keep its variables, so it has states. Borsuk has three kinds of code. The requirement decides the kind, and the compiler checks that the code fits it.

KindUsed whenIts statesWhere the state livesExample
fnThe code performs no effect.NoneRegisters and stackA price rule, a parser
fn … uses {E}The code performs effects for one caller and ends. Each request has a deadline. An all join waits for several requests at once, like Promise.all.Hidden states that the compiler makes, one per waitMemory; lost on a crash, and the caller retriesOne HTTP request handler, a command-line tool
machineThe code has an identity, takes inputs from many senders, and lives longer than one request.Named states that the programmer writes, such as Free, Held, BookedMemory, or a durable store when the machine has a durability nameA booking slot, an account, a session

The envelope

FieldContent
inputThe message, or the answer to an earlier request
nowThe time of this step. It never goes back for one instance. The control plane refuses a node whose clock is far from the others, so one wrong clock cannot move it far ahead.
stepThe instance, a life number and a sequence number. The life number counts how often the instance started from init. Every ticket and message ID comes from it, so an output that a recovery sends again has the same ID.
senderThe authenticated caller and its roles
deadlineThe time after which the caller stops waiting

Every value from outside arrives in the envelope, and the log stores it. So a step is a pure function, and a replay of the log gives the same states and outputs. Random bytes for secrets come from an Entropy request; the log stores that answer encrypted.

Rules for every machine step

  • Pure. The result depends only on the state and the envelope.
  • Bounded. A step has a fixed cost limit. A long computation splits across steps, because a long step delays every instance on its shard.
  • Total. A step returns a result for every input. A fault, such as an integer overflow, is a defined result. The state does not change, and the runtime records the fault.
  • Errors are values. Result and ? carry errors. There are no exceptions.

3b · From code to machine

How plain code becomes a state machine

Rust and C# compile every async function into a state machine. Borsuk does the same for every effectful function. The agent writes plain code, and every tool still sees a state machine. 1 · Plain code

The code reads like a normal functional program. The uses clause lists every effect that the code can perform. ConsoleIn reads and ConsoleOut prints. The read has a deadline, as every request does. sum_lines calls itself as its last action, so it needs no growing stack.

4 · Effects

What code may do outside itself

An effect is a named set of operations that reach outside a pure computation. Examples are a print, a send, a timer and a database read. Each function lists its effects in a uses clause. A function with no clause is pure. The compiler rejects an operation that the clause does not list. So a reader, a reviewer or an agent sees from the signature alone what a function can do. A change that adds a network call must change the signature, and the review shows it.

Each operation is one of two kinds. An output needs no answer: print a line, send an event, start a timer. An output can return an ID that the runtime makes at once, such as the ticket of a timer. A request needs an answer from outside: read a line, read a database row, get random bytes. The code must wait for it, and each request has a deadline.

A machine step never waits. To ask for something, a machine emits the start of the request, for example Db.find.start(Users, id). That start is an output. The answer arrives later as a new input. Because of this rule, every machine step is short and its cost is known.

Library effects are narrow. For example, Db.Read<Users> permits reads of the Users table of an outside database, and nothing else. Requests from a durable machine to the outside world are delivered at least once, with a stable ID. The receiver must drop a copy (section 6).

A private function uses the narrowest form that its callers permit; the task fixes the form of a public one. The type rules for these forms come from "Modal Effect Types" (OOPSLA 2025). A proof of their soundness in the Lean proof assistant is a condition for the v0.1 release.

5 · Example

A worked example: one booking slot

A clinic has appointment slots. A clinic administrator creates each slot. A client first holds a free slot for 30 seconds and gets a hold token. The client then confirms with that token. If the client does not confirm in time, the hold ends and the slot is free again. Many clients compete for one slot, replies get lost, and old timers can fire late. module booking.slot

use booking.types.{Client, ClinicAdmin, HoldToken, SlotId}
use std.timer.{Fired, Ticket, Timer}

pub protocol SlotApi {
    command Confirm(token: HoldToken) -> Unit
        rejects {NoSlot, NotHeld} window 24h
    command Create() -> Unit
        rejects {Exists} window 24h by ClinicAdmin
    command Hold() -> HoldToken
        rejects {NoSlot, Taken} window 24h
    query Owner() -> Option<Client>
}

pub spec SlotSpec on SlotApi {
    law one_owner {
        always count(distinct sender of Confirm -> ()) <= 1
    }
    law owner_is_confirmed {
        Owner() -> map(first(Confirm -> ()), sender)
    }
    law holder_confirms {
        assume shard_up, not_overloaded
        Hold() by c -> t, then Confirm(t) by c within 30s
            implies Confirm(t) -> ()
    }
}

durable quorum(1) machine Slot key SlotId
        implements SlotSpec uses {Timer} {
    state Absent
    state Free
    state Held(holder: Client, hold: HoldToken, timer: Ticket)
    state Booked(owner: Client, hold: HoldToken)

    group Live = Free | Held | Booked

    init Absent

    in Absent {
        on Confirm(_) { reject NoSlot }
        on Create() {
            next Free
            outcome ()
        }
        on Hold() { reject NoSlot }
        on Owner() { answer None }
        on Fired(_) { impossible }
    }

    in Live {
        on Create() { reject Exists }
    }

    in Free {
        on Confirm(_) { reject NotHeld }
        on Hold() {
            let hold = HoldToken.of(env.step)
            let timer = Timer.after(30s)
            next Held(env.sender, hold, timer)
            outcome hold
        }
        on Owner() { answer None }
        on Fired(_) { ignore stale }
    }

    in Held(holder, hold, timer) {
        on Confirm(token) {
            match hold == token && holder == env.sender {
                false => { reject NotHeld }
                true => {
                    Timer.cancel(timer)
                    next Booked(holder, hold)
                    outcome ()
                }
            }
        }
        on Hold() { reject Taken }
        on Owner() { answer None }
        on Fired(ticket) {
            match timer == ticket {
                false => { ignore stale }
                true => { next Free }
            }
        }
    }

    in Booked(owner, hold) {
        on Confirm(token) {
            match hold == token && owner == env.sender {
                false => { reject NotHeld }
                true => {
                    stay
                    outcome ()
                }
            }
        }
        on Hold() { reject Taken }
        on Owner() { answer Some(owner) }
        on Fired(_) { ignore stale }
    }
}

6 · Durability

What survives a crash, and how retries stay safe

Each machine states how much failure its state must survive. The durability name sits on the machine line, for example durable quorum(1) machine Slot …, and it is part of the contract. The author of the code chooses it, as a person chooses a database. A machine with no durability name keeps its state in memory only. Version 0.1 has in-memory machines and durable local. The other names are reserved for a later version (section 13).

The program text never names a store. The deployment file picks one, and the build checks that the store covers every failure that the name lists. So the same program runs on a laptop with a local disk and on a cluster in three zones.

The meaning of each name is fixed for all time. durable zonal means "survives the loss of one zone", so its copies span several zones. durable regional means "survives the loss of one region". An in-memory machine must also state when an idle instance ends, for example expire idle 30m, because a caller can see that loss.

One durable step, in order

  1. AdmitThe runtime looks up the command ID. A known ID gets its stored decision. A full mailbox gets "overloaded", which is not a decision.
  2. ComputeThe pure step runs on the state in memory.
  3. CommitOne log record holds the input, the change to the state, the outputs and the decision. Many steps share one disk flush.
  4. GateReplies and messages wait until the store reports the record as safe at the promised level. A query writes no record. Its answer waits until the last record that it reads is safe.
  5. ReleaseThe platform sends the outputs. Each output has a stable ID.
  6. RecoverAfter a crash, a new writer loads the last checkpoint and reads the log after it.
Crash before the commitNothing left the gate. The record can survive the crash or not. The client sends the command again with the same ID. If the record survived, the client gets the stored decision. If not, the step runs again with a new envelope, so its result can differ. That is safe, because nobody saw the first result.
Crash after the commitThe decision is safe. Recovery sends the outputs again with the same IDs, so a receiver can drop the copy.
ResultWithin the failures that its durability name lists, the system never forgets a decision that a caller saw.

The store

The store contract

Every store implements the same seven operations:

  • open a writer epoch, and refuse writes from every lower epoch
  • append a batch of records
  • report the durable position
  • report a write failure
  • read records from a position
  • store and load a checkpoint, in a format that does not depend on the index
  • trim the log up to a position

A store states which failures it survives. The build compares that list with the durability name of each machine, and refuses a store that covers less.

Personal data and erasure

The type of a field can carry the mark personal, for example a name or an email address. The type also names the field that holds the neutral ID of the person. The runtime encrypts each personal field with a key that belongs to that one person. To erase a person, the system deletes the key. When the last copy of the key expires, every copy of the encrypted bytes is unreadable, also in old logs. This happens within the erasure deadline, a deployment setting, for example 30 days. Inputs with personal fields are the one exception to zero-copy reads. At admission, the runtime encrypts those fields into slots of fixed size.

By default, each log record holds the input and the change to the state. A deployment can choose records that hold only the input, to save space. A machine that reads personal fields cannot use that choice, because a replay after an erasure cannot compute the state again from an input that it cannot read. A replay that meets an erased field reports "content erased".

7 · Instances

Millions of instances on many nodes

Not in v0.1: many nodes

Version 0.1 runs on one node. Its shards run on the cores of that node and own key ranges, as this section describes. The parts for many nodes come after v0.1: the control plane with consensus, the move of a key range to another node, failover, copies of a log on other nodes, and fresh and stale queries on copies. The durability names durable quorum(f), durable zonal and durable regional are reserved.

A machine type such as Slot has one instance per key: Slot(7), Slot(8) and so on. An instance exists logically for every key. The runtime loads it into memory when a message arrives, and removes it from memory when it is idle. The program names the type and the key, and never creates or addresses an instance by hand.

A durable machine starts in Absent. A Create command makes it real, and its by clause states who may send it. So a message to a key that nobody created gets a clear refusal, for example NoSlot.

The two forms have two different laws, so both exist. The deployment selects how a fresh query confirms the writer: a round trip to the log, or a lease with a time limit. A lease is safe only within the lease clock bound, which is shorter than the lease. The evidence record names that assumption.

Overload

  • Bounded queues. Every mailbox and outbox has a capacity. When it is full, the sender gets "overloaded" at once.
  • Pending work is not idle. An instance with an open pending decision stays in memory until it decides.
  • Deadlines are decisions. A command that waits past its deadline after admission gets the stored decision DeadlineExceeded. It never disappears without an answer.
  • Retry budgets. The client library limits its retries, for example to 10 % above its normal rate. "Overloaded" carries a time to wait.
  • Hot keys. One instance has a measured limit of steps per second. Escrow splits a scarce resource across several instances (below).

The cell gives no decision now. It stores a Decision value in the state. A retry of Pay with the same command ID gets Pending.
Decision
The type checker forces exactly one decide for each Decision value, on every path.
Deadlines
The decision deadline (2m) replaces the deadline of the command. The request deadline (90s) must be shorter, so in normal operation the TimedOut answer comes first. If no cell decides by 2m, the runtime stores DeadlineExceeded, which means "result unknown". A later decide then changes only the state. So the caller always gets one decision.
Unknown result
PaymentUnknown tells the caller that the charge may have happened. The charge request carries a stable ID, so a later query to the payment service can find the charge by that ID.

A transaction

bank/transfer.bknotation sketch
transaction Transfer(from: AccountId, to: AccountId, amount: Money) {
    Account(from).Withdraw(amount) accepts outcome _
    Account(to).Deposit(amount) accepts outcome _
}

A transaction is a fixed list of commands to named instances. The list cannot pass a result from one command to the next. Each command states the decisions that it accepts. The commands keep the sender of the caller, so Withdraw still checks the owner. If Withdraw rejects with InsufficientFunds, no account changes.

Global protocols

A global protocol, also called a choreography, is one text that describes every party and every message between them. For each role, the compiler makes a separate machine. That machine talks to other machines only through their protocols. The compiler proves that no party can wait forever on another.

A team can write its own coordination once, as a library global protocol, for example a saga or its own two-phase commit. A transaction then uses it by name: transaction Move(…) via TwoPhase. The checker requires that such a protocol keeps every promise of the built-in transaction.

Escrow

A concert has 10,000 seats and 50,000 buyers in the first minute. One instance cannot take that rate. Escrow splits the seats into parts, for example 100 instances with 100 seats each. Each part sells from its own stock. A part that runs out asks another part for seats. Escrow is a library global protocol with one law. The sum of all parts never exceeds the total.

Not in v0.1: machines with several writers

Some machines accept writes in two regions at once and merge them later. Such a machine cannot promise one decision per command or a fresh read, so v0.1 does not have it. A normal machine can hold a mergeable value as a field. A mergeable value is a data type with a merge function. The merge gives the same result in any order. Examples are a counter and a set that only grows (a CRDT). Other regions can keep read copies for stale queries. The keywords for multi-writer machines are reserved.

8 · Memory and speed

How values live, and where the speed comes from

The speed target compares Borsuk with an expert service in hand-written Rust that keeps its own log. Both run on the same hardware, with the same durability and the same erasure promise. Borsuk must reach at least 95 % of its throughput. Its p99.9 latency (the slowest request in a thousand) may be at most 110 % of the Rust latency. Nobody has measured this yet. It is a target, and the experiments in section 14 test it before v0.1 ships. If the model misses the target, fixed fallback steps apply, and the first three change no program text.

The memory model serves that target and simple proofs. It has no garbage collector, no reference counting and no lifetime annotations.

One signature for each body: the mode function M

The language spec defines one function M from a function body to its signature. The compiler accepts only M(body), and an error message prints it. So an agent never chooses a mode. Five rules make M total:

  • A private function takes a parameter that it passes on to an owner. It never copies the whole parameter.
  • The mode inside a function parameter follows from the body. It is take when each call passes the value at its last use, and read in every other case.
  • The parameters of a private function are in the order of their first use in the body.
  • The mode of a generic parameter is computed for the owned case. A plain type ignores it.
  • The hash of a definition covers the signatures of the functions that it calls, so a changed mode changes the hash of each caller.

A Lean proof shows that M is deterministic. A body edit can change a mode or the order of parameters, and the callers then change too. The tools report how far each edit spreads.

Compaction: storage that stays small

Akka event sourcing keeps every event forever, so the code must read every old event format for all time. Temporal stops a workflow at 51,200 events, and the programmer must restart its history by hand. Borsuk avoids both problems. Each log record holds the change to the state. The runtime takes checkpoints of the current state and then trims the log behind them. Program code never resets a history.

PartRule
CheckpointThe state and the decision table of every instance at one log position, in key order, in canonical bytes, with a format version. It does not depend on the structure of the index. Before the log behind it is trimmed, a second process replays that log segment from the previous checkpoint and compares the state hashes. For a replicated store, a copy node does this replay. So each log segment costs one extra replay, off the hot path.
TrimThe trim waits for the confirmed checkpoint and for every registered reader. The audit archive is one reader. Other readers that fall behind a stated limit lose their place, and restart from a checkpoint.
Dead dataA logged step makes an entry dead: a decision leaves its window, an instance ends, or a key is erased. Each shard keeps one time floor and raises it. Decisions older than the floor leave, with no marker for each one. Compaction removes the bytes later, and that moment changes no answer.
Pacing
  • Each new write gives compaction a fixed amount of work credit.
  • Commits always run before compaction.
  • When the backlog reaches a limit, the shard answers new commands with "overloaded". The same happens when the audit archive falls behind its buffer.
MemoryEach shard has a memory budget. When it is full, durable instances that are idle leave memory first, the least recently used ones first. 9 · Upgrades

Changing a running system

A service runs for years, and its code changes every week. Between two steps, an instance holds only data. It has no stack, no call in progress and no pointer into code. So the time between two steps is a safe point to switch code.

The compiler gives each cell and each function a hash of its normalized text. A release lists the hashes that it needs, so old cells and new cells can live in one release. A new last field with an initial value needs nothing. If a stored state type changes in any other way, the new version must supply a migrate function from the old form to the new form. A proof must show that the spec sees the same state before and after. For example, a migration that maps every booking to "free" fails that proof.

Behavior diff

For each cell and function with a new hash, the tools compare the old code with the new code. The result is "equal, proved", "equal within bounds", or a table of inputs with different decisions, outputs or answers. The shadow run adds the differences on live inputs. A refactor that is "equal, proved" needs no approval. Every behavior change needs a person's approval, also a change that the spec permits. This replaces regression tests.

What the migration proof does not cover

The spec sees only what callers can observe. A migration can lose a private field and still pass the proof. So a migrate must use every old field, or name it in a drop list. The compiler checks this rule, so no test is needed for it. The check step also reports how many instances changed in each field. When the spec itself changes, for example with a new command, the contract diff shows the change, and a person approves it (section 11).

10 · Evidence

How we know that a machine does what it promises

Each machine implements a spec. A spec names the inputs and outputs that callers can see, and states laws about them. The machine's private states can change freely, as long as everything that a caller sees still obeys the laws. A person approves every spec and every change to a spec (section 11). All evidence rests on the spec, so an agent never approves a spec for its own code.

Laws use a small fixed set of forms. So each law has one text, and a tool can decide most laws without help.

The order of the tools

  1. RefuteA bounded check and a directed random search look for a cheap counterexample first.
  2. DecideA decision procedure settles the laws of the simple forms.
  3. SMTThe solver gets a query with only the cell and the definitions that its hash names. Small queries stay stable.
  4. LeanAn agent writes a proof for the hard rest. A small checker confirms it.

Each step has a time budget. A failed step returns a counterexample or the open goal, and an agent uses it to repair the proof. Helper lemmas and invariants live in the evidence store beside the hashes, never in program text. In 2026, agents close proofs far more often with SMT-style tools than in Lean. One benchmark measured Dafny at 82 %, Verus at 44 % and Lean at 27 %. So Lean comes last.

Checks of the spec itself

A proof shows that the code obeys the laws. It cannot show that the laws say enough. In 2026 studies, 22.7 % of specs that a verifier accepted had no postcondition. Programmers judged a wrong assertion correctly in only 49 % of cases. So the tools also measure each spec.

Two levels of checks

A static rule is a rule that the compiler always decides: types, effects, ownership and the full table of cells. A program that breaks one does not compile.

A proof duty is a claim that a tool cannot always settle. Examples: "this cell can never run" (impossible), "this recursion ends" (decreases), "each instance of this in-memory machine reaches a final state" (expire idle never), and a law of an interface. A proof duty gets one of the five results above, and a program release needs "proved" for each one. A spec law is different. The release report shows its result, and the person who approves the spec sets the minimum result for each law. A new solver version can turn "proved" into "unknown". It can never make a program fail to compile. A cell marked impossible that runs anyway gives a stored fault.

A goal of the language is that a team writes as few tests as possible. These are end-to-end checks and tests of critical logic only. The compiler, the runtime and the checker cover the rest.

This goal has a cost. The spec carries the weight that tests carry elsewhere. A person is a weak last guard when the person sees only text. So the approval covers the law strength report, the witnesses and the boundary traces in addition to the text.

Checks in production

The compiler turns each law and each effect contract into a monitor. A monitor is a registered reader of the log, like the audit archive. It runs on a copy node, off the hot path, and reads only the fields that its law names. A violation becomes a "counterexample" record with a replayable trace. One team that ran such monitors on 1,300 pods measured about 2 % CPU and found a bug that was one year old.

A contract probe runs generated request sequences against the test service of an outside system, before each release and on a schedule. One built-in probe sends each request twice with the same ID and checks that the second answer equals the first. Section 6 depends on that property.

Simulation and the compiler

simulate <deployment> runs every machine of a deployment in one deterministic process. Each outside effect uses a fake machine that contract probes checked against the real system. The laws of specs and of global protocols run on the joint trace.

A reference interpreter runs the canonical text directly. The tools compare its state hash and outputs with the compiled step. They do this in simulation, and on 1 % of the steps that the checkpoint replay runs again. A difference is a compiler fault report. It never changes an answer.

Evidence for the runtime

The runtime has its own laws: for the gate, the decision table, tickets, epochs and transactions. Each law gets one of the five results in each of three layers. Layer 1 is a model with proofs. Layer 2 is a simulator that also reads the internal state of each copy. Layer 3 is black-box tests of the real binaries and client libraries, with real disks and networks and mixed versions during an upgrade. Layer 3 exists because a simulator replaces the clock, network and disk code that it does not test. An outside review is part of layer 3.

What an evidence record covers

Each evidence record holds the hashes of:

  • the code and the spec
  • the assumptions and the bounds
  • the deployment platform, the store and its settings
  • the checker that confirms certificates

The record also holds the law strength table and a witness trace for each law. It holds the coverage of each "sampled" result and the behavior diff of each changed hash. A change to any of the hashed parts makes the record stale. A certificate is a proof object that a small checker can confirm again, for example a Lean proof term or a replayable trace. With a certificate, the record does not name the solver that found the proof, so a solver upgrade keeps it valid. Without a certificate, the record names the solver version too. After a change, only the stale records run again.

Features that meet

Each large feature has its own laws. Two correct features can still break a law together. An example is a transaction that spans a shard on new code and a shard on old code. The design lists every pair of features that share a mechanism: a log, a hash, a key, a clock or a mailbox. The list is part of the runtime spec. Before v0.1 ships, each listed pair gets its own law and a bounded model check. The build refuses a program that uses two features that share a mechanism, unless the list has a law for that pair.

Coding agents write Borsuk. People seldom read the text. They read tables, diagrams and traces that tools make from the text. So the language has few choices. Agent QA

A QA agent explores the running system and proposes input sequences. A finding counts only with a replayable trace and a mechanical oracle.   • QA starts from the approved journey statements, then explores freely.
  • The tools rank findings before a person sees them.
  • A finding inside the language never flakes, because the replay is exact.

15 · Consistency

Can this language exist?

Answer

Yes. One model of the language satisfies every rule in this document, and no two rules exclude each other. What remains is measurement (section 14) and the risks below.

The check took every pair of parts and asked whether both can hold at the same time. A conflict means that no consistent language exists. A risk means that the design is consistent, but a measurement must show that it is fast or practical. The check found no conflict.

16 · Future

Toward a universal language

The long-term goal is a universal language in the class of Java, Scala, Rust or TypeScript. It is one language for services, tools, libraries, data processing and user interfaces. Version 0.1 covers services and tools of every size. The hardest rules come from durable services, so most of the design describes them. Nothing in v0.1 limits the language to that use. The three kinds of code are general. A pure fn is ordinary code. An effectful fn is an ordinary program. A machine is a long-lived component. Durability is optional, and the platform decides which effects exist.

Two v0.1 rules help every later use. Floating-point numbers give the same bits on every CPU, so a replay stays exact (section 8). Text is always valid UTF-8, with one pinned Unicode version per release.

User interfaces

Version 0.1 contains no user-interface feature. A later version can describe user interfaces, as a replacement for React and similar frameworks. The reason is that a screen is a state machine. An event comes in, the state changes, and a pure function computes the new view. That is the step model of this language, and the Elm architecture showed that it works for interfaces. Version 0.1 builds nothing for this. It only states five rules, so that no decision blocks the path.

Rule in v0.1What it keeps open
The set of platforms is openA deployment names one platform, and each platform lists its own primitives and the inputs it can send. A browser platform can come later with no change to the language.
The runtime core is a library that a host callsThe core starts no thread and opens no file or socket, and the host gives it the time. One shard on one thread with no store is a legal deployment, which is what a browser tab needs.
The compiler's intermediate representation (IR) and the byte layout are target-neutralNo integer or offset depends on the pointer size, and the IR needs no threads. A WebAssembly target stays possible.
A Foreign contract uses the language's own typesThe list of host languages belongs to the platform: Rust and C on a server, JavaScript in a browser.
A deployment may split a build into load unitsCode can load in parts by hash, as a web page needs, without a change of meaning or of evidence.

Parts of the design that already help

A machine with no durable word compiles with no store code, which keeps a bundle small. A bounded step fits a browser, which flags any task above 50 ms. Hot swap at a step boundary is hot reload that keeps the state. A child component tells its parent through an event, as Phoenix LiveView binds events by name, so no stored callback is needed.

Appendix A

Why every program fits the step model

Borsuk claims that every program that a classical computer can run can be written as state machines with typed effects. This appendix checks that claim. The short answer is yes, when each state can hold typed data. Every real computer is finite, so the useful question is not "finite or not". It is whether the model splits a small control part from a large data part. Borsuk does that split.

Four terms help here. A sum type is a type with a fixed list of cases, like a Rust enum. The control skeleton of a machine is its states and edges with the data removed. Turing-complete means "can compute everything that any computer can compute". Rice's theorem says that no algorithm can decide a non-trivial property of the behavior of every program.

#ClaimResultReason and source
1A program on a physical computer is a finite-state machine.True, but not useful16 GiB of memory holds 1.37×10¹¹ bits, so the computer has 2^(1.37×10¹¹) states. No person or tool can use a model of that size.

5An interactive program is a machine whose effects are typed values.True under one conditionEvery source of nondeterminism must arrive as an input: time, random bits, message order and I/O results. Then each step is a pure function. Mealy machines and coalgebras (Rutten 2000) model this form.
6A distributed system is a set of machines plus channels.TrueEach node runs a state machine. The system is the product of the state machines and their message queues. The P language uses this model at AWS. IronFleet uses it in proofs.

  • Nondeterminism stays outside the stepTime, random bits, message order and I/O results are inputs. So a step is a pure function, and a stored input sequence replays to the same states.
  • Some questions have no algorithmFacts about the data need an invariant with a proof, or a bounded check. The five evidence results in section 10 keep these cases apart.

Why the lowering in section 3b always works

Rust and C# compile every async function to a state machine of the same form. Two classic methods give the general case. Continuation-passing style rewrites a program so that each function receives "the rest of the work" as an argument. Defunctionalization then replaces each such argument with a case of a sum type. The cases are the hidden states of section 3b. The data of each case holds the live variables, which are the variables that the rest of the work still reads. Borsuk applies both methods at each wait point of a fn … uses.
